# Week 4: Advanced SQL for Data Engineering — Core Reference Notes

Structured daily technical notes, debugging rules, and failure modes across relational querying, joins, and analytical window functions.

---

## 📅 Day 1 — Aggregations, Filtering & Query Structure

### ⚠️ Critical Watch-Outs
* **`COUNT()` vs. `SUM()`:** Both return numeric scalars and execute without raising errors.
  * `COUNT(points)`: Measures non-null row presence.
  * `SUM(points)`: Computes the aggregate sum.
  * *Sanity check:* Always evaluate whether the output magnitude represents an unaggregated count or a genuine total.
* **Execution Order (`WHERE` vs. `HAVING`):**
  * `WHERE` evaluates records **before** grouping.
  * `HAVING` filters aggregate partitions **after** grouping.
  * Aggregates like `SUM(...)` cannot be evaluated inside a `WHERE` clause.

### 💡 Engineering Rules
* **PostgreSQL Quoting:** Columns defined with mixed case or camelCase (`"driverRef"`, `"raceId"`) require explicit double quotes; pure lowercase identifiers do not.
* **CTE Redundancy:** If an upstream Common Table Expression already aggregates data to a unique driver grain, repeating `GROUP BY` in the outer query is redundant overhead.
* **CTE Scope:** Avoid wrapping single-stage aggregations in CTEs. Reserve CTEs for multi-layered transforms, recursive operations, or window preparation.
* **Targeted Practice:** When practicing explicit constraints (e.g., selecting exactly 3 columns), avoid adding superfluous projections to keep the target test clean.

## 📅 Day 2 — Relational Joins & Data Integrity

### ⚠️ Critical Watch-Outs
* **Silent Dropped Records:** An `INNER JOIN` silently excludes unmatched rows (e.g., records with orphaned or placeholder IDs disappear unnoticed).
* **Anti-Join Filtering Boundary:**
  * To isolate unmatched records, use a `LEFT JOIN` combined with `WHERE right_table.key IS NULL`.
  * Always test for `NULL` on a primary/join column belonging to the **right-hand** table (`pd.driver_id IS NULL`), never the left-hand table (`pr.driver_id IS NULL`).
* **Hardcoded vs. Dynamic Detection:** Filtering via `= 99` only catches known bad keys. Filtering via `IS NULL` uncovers unknown foreign-key mismatches and orphaned entries.
* **Join Fan-Out & Aggregate Inflation:**
  * Joining a one-to-many relationship without prior reduction duplicates rows from the one-side, inflating downstream calculations (e.g., Bahrain race points inflating from 80 to 123 due to lap-time fan-out).
  * *Fix:* Pre-aggregate the many-side table to the target grain inside a CTE before performing the join.

💡 Engineering Rules
Join Selection Matrix:
   `INNER JOIN`: Preserves strictly matching keys across both tables.
   `LEFT JOIN`: Preserves the complete left-side baseline regardless of right-side presence.
   `FULL OUTER JOIN`: Preserves the complete union of matched and unmatched rows from both tables.
Self-Joins: Join the same physical relation against itself using distinct aliases (`r1`, `r2`) to compare adjacent records or evaluate hierarchies sharing a common key.
Row Count Reconciliation:** Predict and calculate expected output row counts before executing joins to verify cardinality.

📅 Day 3 — Analytical Window Functions

⚠️ Critical Watch-Outs
Tie Handling (`RANK` vs. `DENSE_RANK`):**
   `RANK()` leaves gaps after identical values: four identical values produce `1, 1, 1, 1, 5`.
   `DENSE_RANK()` maintains consecutive numbering: four identical values produce `1, 1, 1, 1, 2`.
Chronological Sequence vs. Sorting: If an explicit date or timestamp is missing, order windows by a deterministic sequence key (e.g., `result_id`). Alphabetical sorting on race names is non-chronological and yields invalid trend analysis.
`NTILE()` Value Splitting: `NTILE(n)` distributes records based on sorted **row position**, not absolute values. Identical numeric values near bucket boundaries can fall into separate quantiles.

💡 Engineering Rules
Window Formulation Framework:** Before writing an `OVER()` clause, explicitly answer:
  1. `PARTITION BY`: At what boundary does the calculation restart?
  2. `ORDER BY`: What chronological or numeric sequence defines the evaluation?
Lagging Transitions (`LAG`):
   To fetch the preceding race result: `LAG(column) OVER (PARTITION BY driver_id ORDER BY result_id)`.
   The initial record per partition automatically returns `NULL`.
Cumulative Metric Accumulation:
   Running total per driver: `SUM(points) OVER (PARTITION BY driver_id ORDER BY result_id)`.
   Neither partitioning by points nor ordering by points produces a driver-level timeline.

📅 Day 4 learnings CTE (Common Table Expression)

1. “One row per ___” means GROUP BY. “Keep every row and add a column” means a window function.
2. For “above the average of the totals”, collapse to totals first, then compare against an aggregate of those totals.
3. ROW_NUMBER() needs an ORDER BY plus a tie-breaker. Top 1 per group is ROW_NUMBER in a CTE, then WHERE rn = 1.
4. A grand total in a window is SUM(x) OVER ().
5. Multiply by 100.0 before dividing, because Postgres divides integers as integers.
6. Aggregate the many-side table before you join it, then check that every race still totals 80.
7. Build a CTE one layer at a time, and run the first layer on its own before adding the next.

The logic behind all of it
- View: a saved query that stores no data. Every SELECT runs it against the tables as they are now.
- CTAS table: a copy of the data at one moment. It never changes unless you rebuild it.
- Temp table: a copy that exists only for your session, so you can reuse it across several statements.
- Materialized view: a copy plus the remembered query, so one REFRESH rebuilds it.
